# CQA Hackathon — план реализации

Стек: FastAPI + SQLite (SQLAlchemy, WAL) + чистый HTML/CSS/JS (без фреймворков, под HTML-компонент Dynamics 365).
Модели: Gemini Flash (ID в `.env`) — основной оценщик; Jev (TypeSafe AI) — независимый второй голос, подключаемый модуль.

## Архитектура оценки

1. Загрузка диалога (GET API по `group_id` через бэкенд, обход CORS). Реплики получают индексы.
2. Извлечение фактов (Gemini, JSON): тип запроса (общий / защищённое действие), нужна ли идентификация, сформулирован ли запрос, обрыв чата, явное ожидание, недовольство клиента.
3. Оценка критериев — два независимых прогона:
   - Gemini: ответ / ступень шкалы, объяснение, индексы реплик-доказательств.
   - Jev (если доступен): Да/Нет/N/A + вероятность, без объяснений.
4. Объединение (код):
   - совпали → ответ Gemini, уверенность высокая;
   - разошлись и у Jev высокая вероятность → Gemini перечитывает критерий, пометка «спорный»;
   - разошлись и вероятность низкая → ответ Gemini, пометка «проверить»;
   - Jev недоступен → только Gemini.
5. Код (не модель): проверка, что цитаты есть в транскрипте; правила N/A; баллы пропорционально весу; перераспределение весов при N/A; итог 0–100, округление до 2 знаков; отдельная отметка грубых ошибок (критерий 08, без баллов).
6. Фидбэк оператору (отдельный вызов, строится только из выставленных оценок и цитат, на балл не влияет).

Правила из чек-листа, которые нужно зашить в промпты и код:
- «Нет» — действие было нужно, но пропущено или сделано неверно; N/A — по условию критерий неприменим.
- Общий вопрос о тарифах → идентификация N/A; защищённое действие без проверки → «Нет».
- Услуга в обход компании: достаточно самого предложения (деньги лично оператору / личный номер клиента).
- Бот и system — только контекст; приветствие бота не засчитывается как контакт оператора.
- Шкалы: критерий 04 — 20/15/10/5/0; критерий 06 — 10/7/4/0. Верхняя ступень = полный вес.
- Порог первой реакции 3 минуты, теги и вложения в оценку не входят.

## Этапы (24 часа)

**Этап 0 — основа (1–2 ч)**
- Репозиторий: `backend/`, `frontend/`, `.env.example` (ключи и ссылка API не коммитятся), README с запуском.
- Схема БД: диалоги, реплики, чек-листы, критерии, оценки по критериям (gemini / jev / итог), апелляции, решения, фидбэк.
- Загрузчик датасета DEV.

**Этап 1 — ядро оценки (5–6 ч), главный**
- Чек-лист как данные; 8 критериев из PDF — стартовая конфигурация; промпт строится из конфигурации.
- Пайплайн из раздела «Архитектура», интерфейс `Classifier` (GeminiClassifier, JevClassifier).
- Юнит-тесты арифметики (веса, N/A, округление, итог без применимых критериев).
- Ручная проверка 15–20 диалогов RU/KZ/EN, настройка промптов.

**Этап 2 — интерфейс оценки (4 ч)**
- Список диалогов, запуск оценки (один / пачкой), карточка: транскрипт + критерии, клик по доказательству скроллит к реплике, плеер для звонков, обе оценки (Gemini / Jev) рядом.

**Этап 3 — апелляция и пересмотр (3 ч)**
- Выбор критерия, комментарий, очередь проверяющего, решение с причиной, пересчёт итога, история: исходная → решение → финал.

**Этап 4 — редактор чек-листа (2–3 ч)**
- Добавление / изменение критериев, веса, типа ответа, N/A, шкалы; сохранение и применение. Репетиция «замена одного критерия + перегон диалогов».

**Этап 5 — бонусы (4–5 ч, только после 1–4)**
- Фидбэк оператору; админская статистика (операторы, языки, критерии, N/A, грубые ошибки, апелляции, стоимость и время).
- По запасу: сводка по оператору, сравнение версий чек-листа, экспорт отчёта, заготовка JSON для CRM (Dynamics 365), облачная транскрибация.

**Этап 6 — финал (последние 3 ч)**
- 23 ч: загрузить 10 контрольных транскриптов, оценить, просмотреть вручную.
- Зафиксировать коммит, README, отправить ссылку организаторам, репетиция защиты на 5 минут.

## Защита (5 минут)
1 мин интерфейс и диалог → 2 мин оценка, обоснование, переход к реплике, пример N/A и итог → 1 мин апелляция, решение, новый итог → 1 мин смена критерия.

## Риски
- Квоты и лимиты Gemini на пакетной оценке — ограничить параллелизм, ретраи.
- Доступ к Jev и качество на RU/KZ — не блокирует остальное.
- KZ-диалоги — проверять отдельно.
- Кэширование результатов по `conversation_id` недопустимо (проверка «корректности процесса»): каждый запуск реально вызывает модель.
- Ссылка API с подписью и ключи — только в `.env`.
